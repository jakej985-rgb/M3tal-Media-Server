**DocCritic Audit Report: M3TAL Platform (v1.4)**

**Verdict: FAILED (BLOCKER)**
As a new user, I cannot successfully deploy this stack. The documentation suffers from "expert bias"—it assumes I know how to handle the build environment, where files should reside, and how to resolve path-based permission issues. The lack of an explicit `.env` template creation process is a critical failure.

---

### Detailed Issue List

#### **BLOCKER**
1.  **Missing `.env` File Generation/Validation:** The docs mention an `API_TOKEN` is generated by `init`, but there is no instruction on whether the user needs to manually create a `.env` file first. If `m3tal init` fails because the file doesn't exist, the setup is broken.
2.  **Hardcoded Path Assumptions:** The documentation says the system "enforces `/mnt` paths," yet the default is `./data`. If a user blindly follows the "enforcement" note and creates `/mnt` (which requires root/sudo), permissions will break on the Docker bind mounts.
3.  **Missing Traefik Gateway Details:** The documentation mentions a Traefik gateway in the prompt instructions but omits it entirely in the README. How is external traffic routed? Is the `8082` port direct to the dashboard, or through a proxy?

#### **WARNING**
4.  **Prerequisite Gap:** You require `Go 1.26+`. As of today, the latest stable Go release is 1.23. Requiring a non-existent version will cause users to panic or install unstable nightly builds.
5.  **Build Instruction Ambiguity:** You suggest `go build -o m3tal ./cmd/m3tal`. If the user has not installed Go dependencies (`go mod download`), this command will fail.
6.  **Dashboard/API Mismatch:** You list `m3tal-godash` as a "Related Project" but imply the current dashboard is "Python-based." Is the current repo using the old Python dashboard or the new Go one? The user doesn't know which code they are running.

#### **SUGGESTION**
7.  **Docker Group Requirement:** Being in the `docker` group is a security risk for some environments. Provide an alternative (e.g., `sudo` usage) or clarify that it is mandatory for the Go binary to control the engine.
8.  **Orchestrator Logs Clarity:** `./m3tal list` is an ambiguous command name for viewing logs. Consider renaming to `./m3tal logs`.

---

### Suggested Fixes

1.  **Environment Fix:** Provide an `env.example` file in the repo.
    *   *Instruction update:* "Copy the template: `cp env.example .env` before running `./m3tal init`."
2.  **Path Clarification:** Explicitly state: "The system defaults to `./data` for portability. If you use `/mnt`, ensure the directory exists and the current user has `rwx` permissions."
3.  **Version Correction:** Correct "Go 1.26+" to the actual required version (likely "1.21+").
4.  **Dependency Setup:** Update the build step:
    ```bash
    go mod tidy
    go build -o m3tal ./cmd/m3tal
    ```
5.  **Gateway/Port Transparency:** If Traefik is used, update the **Service Endpoints** table to reflect internal vs. external ports. If Traefik is not used, remove the mention of it from your architecture guidelines to avoid user confusion.
6.  **Architecture Sync:** Clarify the dashboard implementation. "This version uses the [Python/Go] dashboard. Integration with the high-performance `m3tal-godash` is available in branch `x`."

**DocCritic Note:** *Fix these blockers and provide an `env.example` file. Do not assume the user knows to initialize the Go module environment.*
