### **DocCritic Audit Report: M3TAL Platform (v1.4)**

**Auditor:** Senior DevOps Auditor  
**Verdict:** **REJECTED (DEPLOYMENT BLOCKED)**

The current documentation is a "happy path" abstraction that fails to account for the operational realities of a multi-container Go/Python ecosystem. It assumes the user has deep knowledge of the project's internal directory structure and hidden dependencies.

---

### **Issue List**

#### **BLOCKERS**
1.  **[BLOCKER] Missing Dependency Context:** The documentation assumes `source/m3tal-stack` is a ready-to-run directory. It fails to mention if the user needs to initialize Git submodules or if this directory is generated by the `m3tal` binary.
2.  **[BLOCKER] Traefik/Gateway Omission:** The documentation mentions a `DOMAIN` variable in the `.env` but makes zero mention of Traefik or any Reverse Proxy configuration. If `DOMAIN` is set to something other than `localhost`, the project will fail to route traffic. There is no instruction on how to expose ports or configure TLS.
3.  **[BLOCKER] Binary Execution Context:** The instructions say run `./m3tal up`. It is unclear if `m3tal` requires root/sudo privileges (common for Docker socket access) or specific environmental variables (like `CONFIG_PATH`) to find the stack files.

#### **WARNINGS**
4.  **[WARNING] Hardcoded Host Path:** Mandating `/mnt` is a major anti-pattern for non-Linux/containerized development. It prevents deployment on Windows/macOS and ignores existing user mount points.
5.  **[WARNING] Incomplete `.env` file:** The `.env.example` file is referenced but not provided. Users do not know if `API_TOKEN` needs to be manually generated or if the orchestrator generates it on first boot.
6.  **[WARNING] Python/Dashboard Dependency:** The Dashboard is described as a "Flask" app, but there are no instructions for a `requirements.txt` or `venv` setup. The user will face `ModuleNotFoundError` immediately.

#### **SUGGESTIONS**
7.  **[SUGGESTION] Build Automation:** `go build` steps are manual. Suggest providing a `Makefile` to handle binary builds and cleanup.
8.  **[SUGGESTION] Docker Compose abstraction:** The `troubleshooting` section references `docker compose -f source/m3tal-stack/m3tal-compose.yml`. If the `m3tal` binary wraps this, why are we manually running docker commands? The documentation lacks a clear "Source of Truth" for lifecycle management.

---

### **Required Remediation Steps**

1.  **Update Prerequisites:**
    *   Add: "Python 3.10+ and `pip`" to the prerequisites section.
    *   Add: "Reverse Proxy: Traefik (optional, but recommended for custom domains)."
2.  **Define the Bootstrap:**
    *   Add a step: `pip install -r source/dashboard/requirements.txt`.
    *   Add a step: "Ensure Docker user is in the `docker` group to avoid `sudo` requirement for binary execution."
3.  **Refine Path Handling:**
    *   Change the `/mnt` requirement to: "The orchestrator expects a mount point at `BASE_STORAGE_PATH`. If you do not have `/mnt`, edit your `.env` to point to a local directory (e.g., `./data`)."
4.  **Clarify the Orchestrator:**
    *   Explicitly state: "The `m3tal` binary acts as the controller; do **not** run `docker compose` commands manually unless debugging, as this may cause state desync with the Go Orchestrator."
5.  **Provide Sample .env:**
    *   Include the content of `.env.example` in the documentation so users can verify if they have all required keys.
6.  **Port Access Table:**
    *   Clearly label which ports must be opened on the host firewall (e.g., 80, 443, 5050, 8082).

**Audit Status:** *Awaiting documentation update before re-deployment attempt.*
